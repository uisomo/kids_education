# ✨キラキラ（動きのエフェクト）

練習の動画に、手首・足首（ピアノは手のひら）の動きに合わせた
**細い輪郭だけ** のかざりを乗せる。子どもが見返したくなるように。

元になったのは `~/Downloads/PracticeMotionFX`（Swift パッケージ + ハンドオフ）。
取り込みかたと上流との差分は
[`ios/App/App/PracticeMotionFX/README.md`](../ios/App/App/PracticeMotionFX/README.md)。

## 決めたこと

- **録画には一切さわらない。** `CameraSession` / `AVCaptureMovieFileOutput` /
  音声 / 保存キュー / 焼き込み（`OverlayCompositor`）は変更なし。キラキラは
  「保存が終わった動画」を読んで **別ファイル** を書くだけ。
- **カメラ中のライブ表示はしない。** ハンドオフの指示どおり。フラグで隠すのでは
  なく、上流のライブ用ファイル 3 つを取り込んでいない。画面に重ねたものは
  どのみち録画には入らないので、「見えているのに保存されない」を作らない。
- **いつでも もとに戻せる。** done 画面の「なし」で元の動画に戻る。保存・送信は
  そのとき画面に出ているほうを使う。
- **初期値はオフ。** 押さなければ何も起きないし、何も作られない。
- 通信・アップロード・課金・外部サービス・学習モデルのダウンロードは無し。
  解析結果（JSON）は端末の中だけ。
- iOS 17 未満では機能ごと出ない（`available: false`）。アプリの最低 iOS は
  15.0 のまま上げていない。

## 流れ

```
保存ずみの mp4
  └ VideoMotionAnalyzer.analyze      Vision（体 or 手のポーズ）→ MotionEngine
      └ EffectTimeline (JSON)        Application Support/KarateRecorder/motionfx/
          └ VideoEffectsExporter     SceneBuilder → EffectPainter → CoreImage
              └ <もとの名前>-fx-<かざり>-100.mp4   （tmp。元ファイルはそのまま）
```

- 解析結果は動画ごとに取っておく。かざりを変えても解析はやり直さない
  （書き出しだけ）。動画が消えたら解析結果も消える。
- 同じ「動画 × かざり」の mp4 が既にあれば作り直さず、それを出す。
- 「やめる」で書きかけのファイルは消える。**元の動画は触っていない。**

## 出てくる名前と、あつめかた（2026-09-26 に作り直した）

**一覧を手で書かないこと。** 名前・色・形・どうやったら手に入るかは
`tools/kirakira-glyphs/gen.py` の表ひとつが持っていて、

```bash
python3 tools/kirakira-glyphs/gen.py
```

が `ios/App/App/PracticeMotionFX/Effects.json`（ネイティブが描く）と
`karate-trainer/src/sparkle-catalog.ts`（画面が並べる）の **両方** を書き出す。
2か所に書くと、必ず片方がずれる。

空手は 11 こ、ピアノは 9 こ。**どの描きかたも「腕（肩→肘→手首）に沿って」描く。**
形を宙に貼るのはやめた（下の「ダサい」の節）。

| style | 何をするか |
|---|---|
| `lightning` | 腕にまとわりつく稲妻。枝分かれし、**1秒に14回引き直して**パチパチさせる |
| `spiral` | 腕を**ぐるぐる回る帯**。時間で位相が進むので、腕が止まっていても回り続ける |
| `aura` | 腕ぜんたいが太く光って ゆっくり脈打つ。こぶしの気のたまが大きい |

style によらず共通なのは 2つ: **こぶし（手首・足首）が光る**のと、
**突きが決まると衝撃波の輪が広がる**こと。

空手か ピアノかは **ビルド**（`VITE_APP_FLAVOR`）で決める。動画の中身から
当てたりはしない。

### 一つずつ開く（✨キラキラ タブ）

最初から全部あると、集める理由が無くなる。**開くのは 1回の稽古につき 多くても
1つ。** 決まりは `karate-trainer/src/sparkle-store.ts`（テストは
`tests/karate/sparkle-store.test.ts`）:

| tier | 条件 |
|---|---|
| `start` | 最初から持っている（空手は 🔵 あおい パワー と ⭐️ ほし） |
| `short` | **3分いじょう** のメニューを、飛ばさず最後までやり切る |
| `long` | **休憩が1つも無い 5分いじょう** のメニューを、飛ばさず最後までやり切る |

- `long` を満たした稽古は `short` も満たしている。強いほうから開け、
  `long` が全部そろっていたら `short` を開ける
  （がんばった稽古が「何ももらえなかった」で終わらないように）。
- 帯とちがって **保存したメニューは要らない**。おためしのメニューでも、
  休まず最後までやり切ったならもらえる。
- 持っていないキラキラは done 画面にも家族タブにも出ない。
  キラキラタブでは影と条件だけ見える（何が待っているか分からないと集めない）。
- 確かめるとき: test アプリの 家族 → 🧪テスト用 に
  「✨ ぜんぶ開ける」「↩︎ 最初にもどす」がある。5分の稽古を何度もやらなくていい。

### 帯のコレクション

同じタブの下半分。帯は **メニューごと**（`menu-belt-store`）なので、メニューを
消すとその帯も消えてしまう。集めたものが消えるのは かなしいので、
`belt-collection-store` が「いちばん上まで行った番号」だけを別に残す
（白からその帯までは通ってきた、と考える。帯は1つずつしか上がらない）。

## これは何をしないか

技の良し悪しを見ない。突きの数を数えない。ピアノの音やタッチを見ない。
顔を認識しない。人物を identify しない。**かざりは飾りで、評価ではない。**
キラキラが開く条件も「長さと、やり切ったかどうか」だけで、上手さは見ていない。

追跡が怪しいときは、まちがったところに出すより **出さない**。顔まわりは
（体の点から推定した範囲で）避けるが、指や体に一切かからない保証ではない。
気になったら「なし」に戻せる。

「動きを減らす」（iOS のアクセシビリティ）を入れている端末では、輪だけの
静かな絵になる。

## 元の動画との違い

キラキラ版は **SDR**、長辺 最大 1920px、音は入るが再エンコードされる。
HDR やフル解像度が要るときは元の動画のほうを保存する。

## けいこ中のキラキラ（画面だけ・2026-09-25 時点で調査中）

家族タブ →「稽古中のキラキラ」で親が選ぶ。既定はオフ。選ばれていなければ
解析用のカメラ出力自体を足さないので、負荷はゼロ。

**保存される動画には入らない。** 録画は `AVCaptureMovieFileOutput` が
カメラの絵をそのまま書いていて、画面に重ねたものは入りようがない。
入れるには録画を `AVAssetWriter` に置き換えることになり、音声・PTS・中断復帰・
保存キューを作り直すことになる（＝やっていない）。

作り: `AVCaptureVideoDataOutput` をもう一本足し、プレビュー・録画と同じ
90°回転＋左右反転をかけて Vision に渡す。だから overlay 側では反転を
掛け直さない（`mirrored: false`、`contentMode: .fill`）。
かざりはプレビューの上・web 画面の下の透明ビューに 30fps で描き、
**絵が変わらないコマは描き直さない**。

録画への配慮:
- `alwaysDiscardsLateVideoFrames` は解析出力にだけ付ける（録画は別の出力）
- コマは 1 枚ずつしか受け取らず、返事を待たない。`submit` が false でも
  そのコマは録画されている
- 熱・低電力で回数を落とし、critical で消える。**録画は止めない**
- 中断で消し、復帰で出し直す

### iPhone 16 実機の実測（2026-09-25）

| | |
|---|---|
| 追跡 | 15fps（目標どおり）／thermal 1 のときは 8fps に制限される |
| 1コマ | 13〜15ms |
| 向き | `size 720x1280` = 縦長。回転は効いている |
| 検出 | **体が 2割前後のコマでしか見つからず、手首はほぼ取れない** ← 未解決 |

途中で見つけて直したもの:
- **Vision の初回モデル読み込みが 7.1 秒**。`TrackingBudget` がそれを見て追跡を
  2fps まで落とし、平均が下がるのに十数秒かかるため、短い稽古は前半まるごと
  死んでいた。しかも 2fps だと `MotionEngine` が毎コマ状態を捨てる（0.3秒ルール）
  ので energy が常に 0 になり、**検出が完璧でも何も描けない**。
  → `VisionWarmUp` でプレビュー開始時に空回しして解決（0.5秒）。

### 残っている宿題

手首が取れない理由が未特定。いま `LiveMotionOverlay` は調査用の設定:
`longestAnalysisEdge: 960`（既定 640）、`minimumConfidence: 0.25`（既定 0.45）。
ログの `best` が実際に取れた手首の信頼度なので、その分布を見てから
**しきい値を決め直すこと**。低いまま出荷しない — 確信の無い点に描くより、
出さないほうがいい。

次にやると早いのは、**実機で録った練習動画を macOS 側で同じ Vision に
かけて検出率を見ること**（シミュレータでは body pose が動かないが、macOS では
動く）。画面の写りかたと切り離して、検出そのものを測れる。

## 実写で測った話（2026-09-26）

実機で撮った練習動画 2本を macOS 側で測って、「かざりが出ない／出ても見えない」
の原因を切り分けた。**この 2本は違う理由でダメだった。**

測りかた: `Models / Geometry / MotionEngine / Scene / Timeline / Catalog /
VisionPoseDetector / VideoAnalyzer / EffectPainter` を `#if os(iOS)` →
`#if true`、`import UIKit` → `import CoreGraphics` に置換してコピーし、
`swiftc` で macOS のコマンドとして固める。アプリと同じコードで解析→シーン生成→
`EffectPainter` で実際のコマに重ねて絵を出せるので、**端末に入れる前に目で
確認できる。** 25〜30秒の動画で 1回 90秒ほど。ffmpeg はこの Mac に無い。

### 1本目（フードコートの自撮り・胸から上だけ）= 撮り方の問題

10fps に間引いて `VNDetectHumanBodyPoseRequest`:
体が取れたコマ 91/205 = 44%、手首 conf>=0.45 は 410機会中 **7回 (1.7%)**、
足首 **0回**。手のポーズは 135/205 = 65% で見つかるが wrist 点は弱い。
→ 描く材料が無い。**至近の自撮りでは body pose は成立しない。**

### 2本目（部屋で立って正拳突き・ほぼ全身）= コードの問題

同じ測定で 74%、手首 conf>=0.45 が 512機会中 257回。アプリと同じ設定
（640px / 15fps / conf 0.45）でアンカーは 218/479 コマに出ていた。
**それでも ⚡️ は 32秒で 0回。** 上流の発火条件

```
speed > 2.2 && radialSpeed > 0.6 && extensionRatio > 0.72
```

を分解すると、肩・肘・手首が揃った 298サンプルのうち
speed 25回 / radial 58回 / extension 33回、**3つ同時は 0回**。
さらに 75サンプルは肘か肩が取れず、その場では発火しようがない。
`extensionRatio` は 2D で測るので、**カメラに向かってまっすぐ突く正拳突きは
腕が縮んで見えて 0.19（中央値）にしかならない。** 追い突きの宿命。

出ていた輪のほうも、線 1.6px・半径 13px・濃さ 18%（energy 中央値 0.106）で、
拡大しないと見えない。**「静かに」を狙って、見えない側に振り切っていた。**

### 直したこと

`MotionEngine.swift` の発火条件と `Scene.swift` の見え方の数値
（一覧は [`ios/App/App/PracticeMotionFX/README.md`](../ios/App/App/PracticeMotionFX/README.md)）。
同じ動画で **⚡️ 16回 / 32秒、出力コマの 37% に何か描かれる** ところまで来た。
数値はここを触ればいくらでも足せる／引ける。**実機に入れる前に、上の macOS
ハーネスで必ず絵を見ること。**

### 「サンダーが全然わからない」（2026-09-26・その3）

数値を上げきったあとも、ユーザーの答えは **「今のままだと全く分からない」**
だった。太さや濃さの問題ではなく、**細い輪郭で図形を描くという方針そのもの**が
6歳には読めない、ということ。

作り直した中身は
[`ios/App/App/PracticeMotionFX/README.md`](../ios/App/App/PracticeMotionFX/README.md)
の差分一覧にある。効いたのは順に:

1. **塗りつぶし＋白いふち。** ステッカーと同じ見せかた。道着でも壁でも畳でも
   同じように形が抜ける。線だけだと背景に溶ける。
2. **大きくする。** 短辺の 9.5%（720px の動画で 68px）。以前は 24px だった。
3. **`orb`（気のたま）を足した。** こぶしそのものを光らせる。印は突いた瞬間
   （32秒で 20回）しか出ないが、たまは **手が動いているあいだ ずっと** 出る
   ので、1本の動画の中で見える時間がまるで違う。

同じ動画（`karate-training-29F3FE5B-…`）での実測:

| | 輪／たまの出るコマ | 印の出るコマ |
|---|---|---|
| `kiBlue`（気のたま） | 206 / 957 (21%) | — |
| `star` など sticker | 293 | 104 = 3.5秒ぶん |

形は `tools/kirakira-glyphs/shapes.py` で作って、**先に Mac で絵を見てから**
入れた（`swiftc` で並べた png を見る）。しずくを数式で作ったら ただの葉っぱに、
三日月を「まる引くまる」で作ったら「D」になった — **数式より手で置いた座標の
ほうが読める。**


### 「なんかダサい」（2026-09-26・その4）= 作りの問題

塗りつぶした大きなステッカーにして「分かる」ようにはなったが、返ってきたのは
**「なんかダサい。これじゃやる意味がないから機能ごとドロップする」**。

分かることと かっこいいことは別だった。**宙に浮いた絵をこぶしの横に貼る**
という作り自体が、クリップアートにしか見えない。ほしいのは
「腕の周りをぐるぐる回るサンダーとか炎」— つまり **体にまとわりつくもの**。

だから、点に絵を貼るのをやめて、**骨に沿って描く** ようにした。

1. **骨を通した。** エンジンは肩と肘を もともと見ていた（突きの伸びぐあいの
   判定に使っていた）のに、外には手首しか出していなかった。`FXLimb`
   （肩→肘→手首／尻→膝→足首）を `EffectFrame` に足しただけで、
   「腕にまとわりつく」が書けるようになった。**足りなかったのは検出ではなく
   配管。**
2. **`wrap()`。** 骨の上を道のりで歩きながら、法線方向に `sin(u·turns·2π+phase)`
   で振る。`turns` が「ぐるぐる」、`phase` を時間で進めると回り続け、`jitter`
   を足すと稲妻になる。両端は `sin(πu)` で骨に戻すので宙に浮かない。
   **display 空間（x に aspect を掛ける）で計算する** — 縦長の動画でそのまま
   計算すると、渦が横につぶれた楕円になる。
3. **`.glow`（ネオン管）。** 同じ線を3回重ねる: にじみ（3.4倍・0.22）→
   色（1.7倍・0.45）→ 白い芯（0.55倍・0.95）、重ね方は `plusLighter`。
   **エネルギーに見えるかどうかは ほぼこれで決まる。** 1本の線を引くのとは別物。
4. **`spiral` は腕が止まっていても回る。** 位相が時間で進むから。
   `lightning` は1秒に14回引き直してパチパチさせる（種は時刻から作るので、
   書き出しをやり直しても同じ絵になる）。

同じ動画での実測。**画面に何か出ている時間が、ステッカーの倍以上になった**
（ステッカーは突いた瞬間しか出ないが、腕のかざりは腕が見えているあいだ出る）:

| | 出ているコマ | |
|---|---|---|
| ステッカー（その3） | 104 | 3.5秒ぶん |
| 腕にまとわりつく（その4） | 218 | **7.3秒ぶん** |

### 重さ（実機で測り直すこと）

`.glow` は 1本の線につき 3回引く。1コマの上限は 16本なので、最悪 48回。
前（塗りのステッカー）は 8本 × 1回だった。**書き出しは確実に遅くなる**
（前は 31.9秒の動画で 8.0秒）。Mac では絵しか見ていないので、
実機で測り直すこと。遅すぎたら `EffectPainter` の 3回を 2回に減らすか、
`Scene.swift` の上限 16 を下げる。

稽古中のライブ表示（`OverlayViews`）も同じ描画を通る。**既定はオフ**で、
そもそも手首が取れていない（下の宿題）が、入れるときは 30fps でこの本数を
引けるか先に測ること。

### 焼き込んだ かざりの上で 技が決まる

作り直して初めて見えた別の問題: **自分で焼き込んだアランの絵の上で、衝撃波が
出ていた。** ステッカーの頃は小さくて目立たなかっただけで、前からあったはず。

**最初の見立ては外れた。** 「Vision がキツネを もう一人の人として見つけている」と
思って、人の候補を画面の上 86% に絞る細工を入れたが、直らなかった。
座標を出して（ハーネスの `FXDUMP=<秒>`）ようやく分かった:

```
t=17.87  anch rightWrist(0.55,0.42) e=0.20 c=0.84     ← 本物
         anch rightAnkle(0.74,0.92) e=1.00 c=0.50     ← キツネの上
```

キツネは別人として検出されてなどいなかった。**画面の外にある足首を Vision が
推測して、たまたまキツネの絵の上に置いていた。** 信頼度 0.50（弱い）で
エネルギー 1.00 ——「速く動いた」のではなく、毎コマ飛び回っていただけ。
しかも尻も膝も取れていないので、支えが何も無い点だった。

直しかた（`MotionEngine`）: **裏づけの無い関節（肩・肘／尻・膝 が取れていない）
には、信頼度 0.62 を求める。** となりの関節が支えている点は今までどおり
0.45 で通す — カメラに向かってまっすぐ突くと肘や肩が消えるので、そこを
厳しくすると突きが死ぬ（「その3」の実測）。

**教訓: 絵を見て原因を当てにいかない。座標を出す。** 当て推量のほうは消した。
