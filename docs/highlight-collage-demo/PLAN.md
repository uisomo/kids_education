# 共通ハイライト・コラージュHook設計案

2026-09-29。空手で先行検討し、アランシリーズ全アプリへ反映する。ユーザー指定の演出仕様と、以下の実装案・検証目標は区別する。本フォルダのデモは構図検討用。アプリへの組み込み・端末性能検証は未実施。

## 1. 確定した動画の流れ

1. **最初のデコード可能なフレームからコラージュ＋Hook全文を表示する。** 黒画面やタイトルがまだないフレームを先行させない。Hookの読み進めは色・小さな強調で表す。全文を消して一文字ずつ出す従来方式は使わない。
2. Hook中、右下に「今日のハイライト」と**縦長の動画を1本だけ**表示する。第0フレームからハイライト1を再生し、3秒で2、6秒で3へ進む。横並び3枚の予告は使わない。コラージュだけ／Hookだけで静止する前置きは設けない。
3. Hook発話終了時、**その時点の再生位置を保ったまま**小窓を拡大する。既に小窓で見せた部分を再生し直さない。3／3／4秒は小窓と拡大後を通算した10秒。拡大の0.3秒もこの時計内に含む。本番の終了時刻は音声境界を使う。
4. 残りのハイライトを見せたら本編へ。Hookが10秒を超える例外では最後の小窓フレームを保持し、発話終了後に本編へ進む（設計上の暫定処理）。本編に既存Hookが焼き込まれている場合は元Hook区間を除く。本デモの既成録画は区間メタデータがなく全編を使用するため、この除外は未実装。
5. ハイライトと本編のバーは維持する。ハイライトは3:3:4、本編は元動画の3区間と現在位置。小窓中も全体の進捗を下部に表示する。
6. 空手・ピアノのFX／効果音／軽いズームはハイライトの10秒内だけ。小窓も同じ再生区間に含まれる。全画面になってから再度同じFXを発火しない。本編へは追加しない。

**今回の確認用時間**：Hookは無音の4秒仮置き。0–3秒＝小窓1、3–4秒＝小窓2、4秒から拡大し2の続き、6–10秒＝3、10秒から本編。Hook文はユーザー指定の「一番の技、どれですか？ 教えてください」。文字起こしから取得したとは扱わない。

## 2. 現在の空手アプリとの差

- `karate-trainer/src/app.ts` の `playTextHook()` は録画開始時のプリセット／入力文を表示する。未来の録画映像を使うコラージュはこの段階では生成できない。録画中の操作用Hookと、保存する動画の編集Hookを分離する。
- `KarateRecorder/OverlayCompositor.swift` は音声を混ぜ、Core Animationの文字等を合成して全編を書き出す。
- `KarateRecorderPlugin.applyMotionEffects()` は完成済み動画に別途エフェクトを付けて再書き出しする。今の経路へさらにコラージュ処理を後付けすると全編の再エンコードが増える。
- `PracticeMotionFX/VideoAnalyzer.swift` は空手の全編で姿勢推定する。ピアノは音声解析の分岐が既にある。ハイライト選定と10秒周辺だけの精密解析を分離すると、空手の負荷削減が期待できる。
- 空手の録画経路には、発話の単語時刻付き文字起こしがまだ接続されていない。他アプリの `SpeechTranscriber` を共有インターフェースへ整理する必要がある。
- 作業開始時点で録画・音声・描画周辺に既存の未コミット変更がある。本検討ではそれらを変更しない。

## 3. 素材とHookの生成

`SourceFacts` に録画ID、実際のフレーム時刻、発話の開始・終了・信頼度、アプリの練習イベントを保持する。Hookとコラージュ内の文字はその根拠へ参照を持つ。デザイン内のダミーの英語、新聞文章、誕生日、作者署名、ロゴ、参照作品の人物・花・建物・写真はコピーしない。

- コラージュの写真は録画から抽出。人物、手、動作、演奏の手元、実際に映った道具などを使う。人物不在のアプリはゲームや課題の録画フレームへ置換する。
- 新聞風の文字面も文字起こしから構成する。単に参照画像の新聞テクスチャを切り出すと元の文が残るため不可。紙の粒子・罫線・幾何図形は内容を持たない描画プリミティブとして作る。
- 発話がない／認識に失敗した際に発言や成果を捏造しない。録画上で確認できる課題名等から短いタイトルを作り、「発話なし」の状態を持つ。デモの装飾文字「正拳突き」は映像内の課題名。Hookはユーザー指定文であり、音声の文字起こしとは扱わない。
- Hookの音声を新たに生成するか、元の発話を使うかは既存の録画方式ごとの接続点とする。原音を使う場合は同一の発話テキストと時間境界を使う。音声なし時のデモ保持時間を、本番の発話時間と混同しない。
- フォントはテンプレートの役割で指定する（太い角ゴシック、明朝、幅を抑えた見出し、手書き系など）。日本語グリフがあること・同梱条件・実機での改行を確認する。デザインに合わせたHookフォントは、従来のM PLUS固定に対する今回の動画限定の変更。アプリ画面全体のフォントは変更対象ではない。
- スマホの縮小表示で読めるHook専用領域を設け、右下の縦長小窓と重ならないよう文字量に応じて改行・縮小を制限する。
- 顔かくし・背景非表示が有効な場合、コラージュ／小窓／先頭フレームも同じ処理後の素材だけを使う。元動画への切り戻しで設定が外れないようにする。

## 4. ハイライトの選び方

選定はランダムにしない。ランダムなのはテンプレートと配色。ハイライトは実際の録画の良い場面を選ぶ。

- 共通：アプリのイベントログ、発話時刻、音量変化、低解像度の疎なフレームで候補を作る。始める準備、休憩、カメラを触る場面、遮蔽や強いブレは除外する。
- 空手：異なる動作・練習区間から、構え→動作→決まりが収まる場面。単純に動きが最大の箇所を採るとカメラ調整が選ばれるため、身体の可視性とイベント範囲を使う。
- ピアノ：音のまとまり・区切りを優先し、単に最大音量や打鍵数だけで選ばない。切れ目が不自然な場合は開始時刻を調整する。
- 他アプリ：本人が語った気づき、挑戦の前後、課題の達成イベントなどを共通候補形式へ変換する。人のポーズ検出を全アプリへ要求しない。
- 重複しない3区間を選び、原則は元動画の時系列順。3／3／4秒の中で意味が成立するよう切る。最後の4秒に結果や余韻を収める。
- 不足時：10秒以上なら離れた有効区間を採用。10秒未満の録画や1場面しかない録画では「3つの異なるシーン」は保証できない。静止保持で長さを補う案を明示し、3場面あったことにはしない。短すぎる動画の扱いは品質検証で確定する。

## 5. 共通化するデータと責務

基盤 `packages/media` と `ios/AlanKit` を正本にし、アプリごとに29種類のレンダラーを複製しない。

- `HighlightPlan`：元の3区間、出力の3区間、Hook区間、本編開始、source↔output時刻変換、ズーム中心、効果音イベント。CMTime等の有理時間で保持する。
- `CollageTemplate`：ID、参照ファイルとパネル番号、レイヤー順、写真スロット、切り抜き／シルエット、テキストスロット、フォント分類、パレット関係、9:16／16:9の配置。組み写真を一枚のテンプレートに潰さず個別IDを設ける。
- `CollageChoice`：ランダムseed・テンプレートID・色パラメータを録画ごとに一度だけ保存。プレビュー、先頭フレーム、再試行、完成動画は同じ値を使う。再レンダリングのたびに見た目が変わることは避ける。
- `TemplateRenderer`：動画の必要静止画＋文字＋処理済み人物マスクから、Hook期間中に再利用する背景一枚を作る。文字読み進めと小窓は薄い別レイヤー。
- `HighlightSelector` のアプリ別差し込み口だけ空手／ピアノ／発話／ゲームで変える。共通側は決まったプランを描く。

## 6. ランダム配色

テンプレートは全29案から等確率、毎回独立抽選。前回と同じ案や同じ色が続くことも許す。日付固定・前回除外・アプリブランド色固定を今回のコラージュに適用しない。

各テンプレートの色を「紙／インク／主色／アクセント」の役割で定義し、OKLCHで基準色相に対する相対角・明度差・彩度比を保存。共通の色相回転 `h_i'=(h_i+Δh) mod 360` で補色・類似色の関係を保持する。明度の順序やコントラストは別制約として保つ。元が青＋黄でも知覚色空間で厳密な180°とは限らないため、元の関係を勝手に補色へ置き換えない。

色域外はRGB値の単純切り捨てを避け、色相と明度を保持してパレット全体の彩度を共通係数で下げる。文字は4.5:1を初期可読性目標とし、満たせない候補を再抽選する。色のランダム性はこの許容集合内で定義する。白黒テンプレートも紙／インクの明暗を保った有彩色版を作れるようにする。写真の肌・道着を無条件に色回転せず、参照が指定するモノクロ・二色刷りのレイヤーだけに色変換を適用する。

## 7. レンダリングを増やさない実装案

最有力案は**元動画から最終動画まで、最終エンコードを1回にまとめる**こと。コラージュ生成や解析は事前処理であり、10秒追加分の書き出し自体は増える。「必ず今より速い」は実測前に保証しない。

1. 録画中に既存イベントを保存し、使える音声認識結果を蓄える。カメラ・マイクに別のtapを重ねない。
2. 終了後、安い候補抽出→3区間決定→コラージュ用の必要フレームだけ抽出。人物マスクは静止画ごとに1回。毎フレームでコラージュを作り直さない。
3. 空手の精密姿勢解析は選ばれた10秒＋各区間の前後のウォームアップ部分のみ。タイムレンジ付きデコードに変え、全編を読み飛ばしてから分析する実装を避ける。光跡の履歴が切断面で飛ばないよう、区間ごとに状態をリセットする。
4. ピアノは既存の音声解析を再利用。文字起こし、VAD、音の特徴を同じPCMから得られるか検討し、重複したデコードを減らす。
5. AVMutableCompositionで3クリップ・本編を並べ、Hookは冒頭のハイライトと時間を重ね、元音声／声／BGM／効果音も同じ編集プランで移動する。エフェクト時刻を再マッピングし、ずれたタイムラインを使い回さない。
6. カスタムAVVideoCompositingの中で、映像→必要なプライバシー処理→ハイライト限定FX／ズーム→コラージュ・Hook・バー・既存字幕を合成する。Core Image handlerとCore Animation字幕の単純併用を前提にせず、現在の字幕が落ちない経路を試作して確かめる。
7. 静止素材・紙・ハーフトーン・文字をテクスチャとしてキャッシュ。毎フレームでフォント計測、画像ロード、JPEG化をしない。マスクやCIContextの再利用、CVPixelBufferPool、使用終了したテンプレート画像の解放を行う。
8. 最終書き出しは既存解像度・fpsを基準とする。性能のために無断で画質を下げない。ハードウェアエンコーダの経路を実機で測る。

代替の「冒頭だけを書き出して本編を無変換連結」は、本編のタイムライン焼き込みと競合する。コーデック／解像度／色空間／GOPの一致も要るため、標準案にしない。デモでは比較の速さを優先して共有ハイライトクリップを再利用するが、それを本番の書き出し性能の証明にはしない。

## 8. デモと検証

添付29ファイルを全て対応表に含める。IMG_3895は9マスで1枚、IMG_3897も6パネル全体で1案、合計29案。IMG_3898の切断ポートレートも独立案。スクリーンショットのPinterest UI・透かしはデザイン対象外。

構図デモ：実写の同じ空手動画から写真・人物切り抜きを取得し、29種類のFirst Frameを作る。比較用の元配色と色替えを同一素材で見られるようにする。元の作品の人物・文字はデモへ混ぜない。装飾文字は映像内の課題名・日時、冒頭Hookはユーザー指定文を使用する。**発話文字起こし由来Hook、Hook発話同期、本番品質の全装飾、アプリ内実装、実機性能検証はこの構図デモとは別工程。**

全テンプレートの動画検証では、同じ10秒の選定素材を共有し、各案のHook＋ズーム移行＋3/3/4秒＋本編の先頭まで確認する。短いHook、長い日本語、人物なし、横動画でも文字・小窓が衝突しないことを確認する。視覚検証に合格していないテンプレートを、本番の抽選対象に入れない。

性能比較は同じiPhone（まず既存テスト端末SE）、同じ入力・出力条件で現行と比較。30秒／3分／10分の空手・ピアノで、解析・静止画生成・合成・エンコード・全処理時間、ピークメモリ、発熱、音ズレ、失敗時再試行を記録する。各条件の温度をそろえ、順番を入れ替えて3回以上測る。目標はコラージュ事前処理の長さ非依存化、10秒外のFX処理ゼロ、全編の重複エンコードゼロ。追加処理が許容範囲かは実測値で決める。

受入条件：
- 完成MP4の第0フレームにHook全文とコラージュが焼き込まれている（ポスター設定だけでは不可）。
- ハイライトは出力時間で3/3/4秒。音と動作の同期は1出力フレーム以内を目標。
- Hook終了、ハイライト切替、本編復帰で音の重複・消失がない。声／ピアノ音が効果音に埋もれない。
- 本編のバーが元動画の3区間に一致する。元時刻と出力時刻の混同がない。
- FX・効果音・演出ズームが10秒外に漏れない。人物検出が欠けたフレームでもエラー停止しない。
- 抽選seedを保存し、再試行でテンプレートと色が変わらない。通常の新規動画では同一案の連続も許容。
- フォント・色域・読みやすさを29案すべて検証する。サムネイルや小窓にもプライバシー設定が適用される。

## 9. 実装順序

1. 本設計・29案の構図を確認。画像の対応と動画素材の来歴を固定。
2. 基盤で編集プラン・色計算・テンプレート定義・時間変換を作る。境界時間と色の関係をユニットテスト。
3. 空手で単一書き出しの試作を1案で行い、現行との実測比較。音声・既存字幕・保存再開を検証。
4. 29案を本番レンダラーで仕上げ、全案のMP4／First Frame／配色見本を自動生成し検品。デモ用Pythonの描画をアプリへそのまま持ち込まない。
5. 空手のテストアプリへ反映。ピアノを次に入れ、その後各アプリの候補抽出・縦横比・音声方式を接続。録画機能のないアプリは録画の導入要件から整理する。

## 2026-09-30：部位とレイヤーの契約

1. 録画開始時の確定済みPrivacySettingsを素材キャッシュキーに含める。camera / roomReplaced / avatar / faceMaskedの素材経路を混ぜない。仮面がアバターなら実写を一切使わず、アバターリグの顔・目・胸・腰の領域を入力する。背景を隠す設定では部屋を再表示しない。写真小窓・First Frameも同じ経路。
2. 候補静止画だけで顔ランドマーク・肩・腰を解析。各枠はface / eyes / eyesAndNose / head / chestToHead / waistToHeadを要求。必要な部位が検出できなければ別候補へ移り、胴体などへの無言の代用はしない。複数人は顔と身体を対応付ける。
3. テンプレートは枠の座標、z順、矩形／楕円／不定形クリップ、人物だけ枠からはみ出すレイヤー、背景色、粒子、グラデーション、文字の回転・書体・行間を明記する。文字は実在書体のポイントサイズと改行で調整し、縦横別スケールを禁止。
4. 顔を保護する領域が必ず入るようクロップを広げる。素材の外にはデザイン背景を置く。目だけの枠は目ランドマークの領域を使う。向き・鏡映後の左上原点0〜1に統一し、左右逆転した部位が別扱いにならないようにする。
5. 部位解析・人物マスク・静的背景を録画単位でキャッシュ。テンプレートや色の再抽選では再解析しない。フレームごとの顔認識やクラウド背景生成は行わない。写真・質感・文字を1枚に事前合成して動画に使用。

共通側に `AlanKit/CollageAnatomy.swift` を追加。顔・身体検出、部位ごとのクロップ計算、PrivacySettingsと素材種類の照合を提供する。まだ空手の本番書き出し処理からは呼んでいない。アバターの部位マップ接続・保護済み素材キャッシュ・最終レンダラーへの接続は今後の実装工程。

デモの `checks/3878-layout.json` と `checks/3895-layout.json` は各枠の元フレーム、検出部位、クロップ矩形、枠座標、ランドマーク変換結果、文字の書体・サイズ・回転を記録する。デモに実際のPrivacySettingsの履歴がないため、おへやON／かめんOFFを比較用に明示し、本人の録画設定として推定しない。

## 最新改訂7：ロゴの鮮やかさ
正式な空手ロゴの不透明・明るい有彩色を測定し、HSV彩度中央値0.973／明度中央値0.988を確認。パステル化の原因だった高いOKLCH明度＋全色共通の彩度圧縮を廃止。有彩色の役割はS=0.90〜0.98、V=0.94〜0.99に固定し、HSV色相だけ全色同角度で抽選。白黒写真・墨色は保持。これは知覚的な明度一定の回転ではなく、ロゴに近い鮮やかさを保つRGB内の配色方式。
